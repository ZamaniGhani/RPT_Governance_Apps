1 RPT Governance Platform — architecture position, then the console
What I took from your answers

Responsive web, no native app. Four roles: company secretary, finance submitter, compliance officer, and every employee once a year for their declaration. Greenfield, so no integration constraints — but also no ERP feed, which means intake is manual and the screening has to happen at the keystroke, not in a nightly batch.

The console ships empty

No sample records. Every party, case, evaluation and audit event you see below is one you create through Intake — which is the honest way to judge the flow, because the first month of a governance system is spent on an empty register. Each tab carries its own empty state and its own first-run instruction.

Where I push back

"Fully modelled MMLR Chapter 10" is the right ambition and the main source of debt if done naively. Thresholds must be versioned data, not code, and every decision must pin the rule-set version it was judged under. ADR-02 and ADR-03 below. I'd also refuse a configurable workflow builder.

Bounded contexts — one modular monolith, six modules, separate schemas
Party Registry
Persons, entities, directorships, shareholdings, family links — effective-dated edges. Owns the relatedness graph and answers "who was related to whom on 14 March".
Transaction Intake
RPT and RRPT records, counterparties, consideration, documents. Screens every counterparty against the graph as it is typed.
Materiality Engine
Percentage-ratio tests, 12-month aggregation, RRPT mandate consumption. Pure functions over a versioned rule set; knows nothing about workflow.
Approval Workflow
A state machine per case type: interested-party exclusion, quorum, abstention. Declarative route definitions, not a general BPM.
Declarations (COI)
Annual campaigns and event-driven declarations. Writes a proposal to Party Registry, never a direct edit — the secretariat confirms.
Disclosure & Audit
Append-only event log, announcement and circular packs, the annual-report RPT schedule. Read-only projections; the retention boundary.
The store — PostgreSQL, one database, a schema per module

registry

party(id, kind[person|entity], legal_name,
      nric_or_reg_no, created_at)
party_relation(id, from_party, to_party,
      basis[spouse|child|director|shareholder|
            control|associate], source[declared|
            detected|manual], confidence,
      effective_from, effective_to,
      confirmed_by, confirmed_at)
No UPDATE on party_relation — a change closes the row with effective_to and inserts a successor. Every register query carries an as-at date; the default is now().

intake

rpt_case(id, ref, kind[rpt|rrpt],
      counterparty_party_id, nature,
      consideration_myr, currency, fx_rate,
      transaction_date, submitted_by,
      rule_set_version, route_version, status)
rpt_document(id, case_id, kind, filename,
      byte_size, sha256, uploaded_by, at)
rule_set_version and route_version are written at creation and never migrated. Documents are content-addressed by hash so an evidence pack can prove nothing was swapped.

materiality

rule_set(version, effective_from,
      thresholds jsonb, retired_at)
financial_period(id, entity_scope, label,
      basis[audited|unaudited|proforma],
      period_end, net_assets, total_assets,
      market_cap, net_profit,
      source_document_id, confirmed_by)
materiality_evaluation(id, case_id,
      rule_set_version, financial_period_id,
      ratios jsonb, aggregate_myr, gate,
      computed_at)
Evaluations are stored, not recomputed on read. A ratio shown to an approver in 2026 must still render identically in 2031 after four rule sets and five financial years.

workflow · declarations · audit

approval_step(id, case_id, seq, role,
      actor_id, decision, rationale,
      decided_at, excluded_reason)
mandate(id, party_id, period, ceiling_myr,
      consumed_myr, approved_at)
declaration(id, campaign_id, person_id,
      status, submitted_at)
declared_interest(id, declaration_id,
      entity_name, nature,
      proposed_party_relation_id)
event(id, aggregate_type, aggregate_id, seq,
      type, payload jsonb, actor_id,
      occurred_at, prev_hash, hash)
event is append-only and hash-chained, unique on (aggregate_id, seq). Write permission is granted to one role; nothing in the application can issue DELETE against it.
Decisions — and what each one costs
ADR-01

Modular monolith, not microservices

A listed company runs a few hundred RPTs a year. Microservices buy scale you will never need and charge you distributed transactions across a graph that must stay consistent. Modules keep separate schemas and communicate through published events, so extraction remains possible later.
Cost: boundaries are discipline, not runtime. Enforce with import linting in CI.

ADR-02

Declarative routes, not a workflow builder

A drag-and-drop approval designer becomes an untestable graph nobody can audit. Instead: versioned route definitions that go through code review, each an explicit state machine with typed guards. A case pins its route version at creation, so a later rule change never rewrites history.
Cost: a new route needs a release, not an admin screen. In exchange every approval is reproducible years later.

ADR-03

Thresholds as effective-dated data

Chapter 10 changes. The 0.25% announcement trigger, the 5% circular-and-approval trigger, the RRPT floor and the 12-month aggregation window live in a versioned rule set evaluated against the transaction's own date — never if (ratio > 0.05) inside a service.
Cost: rule authoring needs its own test harness and a golden-case suite. Non-optional if "fully modelled" is to mean anything.

ADR-04

Event sourcing only where it earns it

Party Registry and Disclosure & Audit are append-only, because the questions asked of them are historical. Everything else stays ordinary CRUD with change-data audit rows.
Cost: two persistence idioms in one codebase. Cheaper than taxing every simple form with an event store.

ADR-05

Screening at the keystroke, not in a batch

With no ERP feed, the only moment you can catch an unflagged related party is while the submitter is typing. Counterparty screening and ratio evaluation are synchronous read-model queries behind a 150 ms budget; the graph projection is denormalised for exactly this call.
Cost: a projection to keep warm and invalidate on every registry change.

ADR-06

Uploaded financials are a period, not a setting

A balance sheet and P&L upload creates a new financial_period row and a hashed source document — it never overwrites the denominators in place. Extracted figures land unconfirmed; a human confirms before any case may cite them, and each evaluation stores the period id it used.
Cost: a confirmation step between upload and use, and parsing that must degrade to manual entry. The alternative — editable global numbers — silently rewrites the materiality of every historic case.

ADR-07

Conflict detection suggests; a human confirms

Traversal proposes a conflict with a confidence and a visible reason path. Auto-blocking on fuzzy name matches produces false positives that destroy trust in the register within a quarter.
Cost: a standing review queue for the secretariat. That queue is the control, not a defect.
